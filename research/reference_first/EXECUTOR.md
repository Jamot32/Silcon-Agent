# Reference-example executor — research only

This isolated prototype checks a validated reference model against directed literal examples before any RTL is run. The host validates the supplied contract, model and examples through `validate_reference_bundle`; it never compiles, imports, or executes the proposed model. It writes the validated data and source to a read-only container input, together with a separately authored driver. The driver compiles and executes the model inside the pinned, networkless Docker image with read-only root, dropped capabilities, and CPU, memory, PID and wall-time limits.

Each case gets a fresh model instance. For the synchronous profile, the driver calls `reset()` once before the first step, ignores its return, then runs each step including the required initial asserted-reset edge. For the combinational profile, it calls `evaluate()` on each step. Every result must be a plain dictionary with exactly the declared output names and plain nonnegative integers fitting the declared widths. The model result is compared with the provided literals. The host separately checks the actual process exit and timeout, reads at most 65,537 bytes of JSON, rejects duplicate fields and malformed or inconsistent counts/indices, and classifies setup errors, model exceptions, invalid output, literal disagreement, process errors, timeout, and malformed observations separately. All are qualification outcomes; none is an RTL functional verdict.

Run from this isolated checkout root using a new evidence directory:

```sh
uv run --no-project --offline --python 3.12.13 python -B research/reference_first/test_executor.py
PYTHONPATH="$PWD/backend:$PWD/research/reference_first" \
  SA_REFERENCE_EXEC_EVIDENCE="$PWD/research/reference_first/executor-evidence-002" \
  uv run --no-project --offline --python 3.12.13 python -B research/reference_first/executor_controls.py
```

The first real control, `executor-evidence-001/`, used hand-worked values for a neutral 3-bit saturating accumulator. The deliberately wrapping model disagreed at its third step; the good model matched all seven steps; an output containing `True` was rejected as invalid; and a model dividing by zero was reported as a model error. All four Docker host processes returned zero without timeout, so the semantic result comes from the recorded observation reconciled with that host receipt. The report SHA-256 is `80a0fee157725b2b33951a0c9d0a5eb511e9e5b652a253e2006e43a6f6cd0aca`. Input hashes were equal at the named before/after points. Synthetic tests also exercise setup/timeout/process failure and invalid observation classification; those are not claims that a real timeout or setup failure occurred in this control.

This is a research artifact, not an integrated production runner. The AST checks, restricted Python builtins, model and in-container driver do not prove purity, isolation against arbitrary adversarial code, or that observations cannot be manipulated by code in the same process. Docker and trusted host receipts are assumed; hashes record point observations, not continuous or loaded-code attestation. The source authorship IDs are labels, not proof that authors reasoned independently, and examples may share an error with a model. The control does not establish arbitrary-design correctness, cost or DEV success improvement, held-out performance, packaging custody, or chip signoff. Synchronous reset semantics, unknown signals, multiple clocks, asynchronous behavior, real sandbox integration and later RTL comparison need separate evaluation.

## Owned-container cleanup control

The updated host launcher attempts removal only for the unique `sa-ref-exec-<32 hex>` name assigned to its own Docker invocation, then reaps its own CLI child. On an interruption during that invocation, it records the interruption and cleanup result before propagating the interruption. Synthetic controls cover interruptions, reaping, failed or interrupted cleanup, rejection of non-owned names, and receipt-before-propagation. A failed cleanup is recorded as failed or unknown; it is not proof that a container is gone. A forced process kill, host crash, a second interrupt while persisting a receipt, or loss of Docker access can still prevent conclusive cleanup or receipt persistence.

A separate real neutral timeout control starts only a sleeping process in the pinned container, observes its start marker, and times out after 3 seconds. In attempt 002, removal returned 0, the owned Docker client was reaped with 137, and a subsequent inspect of that exact name returned no such object. Its receipt SHA-256 is `619a578dcfd98d4807b22363323c96eb411eae62a8f7bb597606279d015eb061`; the separate captured outer command receipt has exit 0 and SHA-256 `5a3bfe1cd2761394a66ebe4a317d39f9c52416c3ded6cdd43a18a041330ad9ab`. This is a real timeout, not a real KeyboardInterrupt test. Attempt 001 is retained: its removal and inspect behaved as expected, but its outer command exited 1 because the control incorrectly matched an uppercase error message. Its exact first control source is archived under `archive-timeout-001/`.

After the launcher change, the four model/example controls were repeated in `executor-evidence-002/` with the same outcomes. The outer capture helper is research scaffolding: if its own 60-second limit or an external interruption kills the control before it completes, owned-container cleanup is not established by that outer receipt.

A later host-only change preserves the original interruption if hashing or receipt writing raises a second exception: the original object is propagated with a sanitized secondary-error note saying the receipt is not confirmed. Synthetic tests cover both hash and receipt-write failures; a missing or partially written receipt is never represented as a confirmed one. The actual 002 controls above measured the preceding host source, archived in `archive-executor-002/`; the later finalization change has not been rerun through Docker.
